# Specification 002 Plan — Provenance, License, and SBOM Machinery

## Objective

Turn Himsat's donor/licensing policy into a small executable admission gate before any donor bytes or third-party runtime dependency are introduced.

## Canonical base

```text
base = 90fc14196a4d5ce486d068e1fc6c45c19e2cc7f0
```

## Design choices

### 1. Governance tool, not product runtime

Implement `tools/provenance.py` with Python 3.13 standard library only. Do not alter Cargo manifests or add Python packages.

Subcommands should remain explicit and auditable, for example:

```text
validate
render-notices
render-sbom
check-generated
self-test
```

Exact names may be refined during implementation if behavior stays bounded.

### 2. Versioned JSON policy and registry

Use deterministic JSON files with explicit schema versions. The policy owns license classification; the registry owns exact adopted objects. Unknown fields/versions should fail according to a documented forward-compatibility policy rather than being silently ignored.

The initial real registry has no adopted third-party entries.

### 3. Exact source/artifact identity

Non-reference code adoption requires an immutable Git revision and repository-relative source paths. COPY/VENDOR and separately distributed model/data/font/asset records carry SHA-256 integrity evidence. DEPEND entries bind package identity to local lockfile observations.

Do not infer path-level license from a repository homepage or engine license.

### 4. Deterministic Cargo closure

Read root `Cargo.toml`/`Cargo.lock` using bounded local parsing sufficient for the current workspace. Every external locked Rust package must have an approved dependency record. Avoid building a general Cargo parser beyond what acceptance requires.

### 5. Generated notices and project SBOM

Generate stable-sorted notices and `himsat.sbom/v1`. Run generation twice in tests to prove byte-for-byte idempotence. CI compares generated bytes with checked-in outputs.

### 6. Fixture-driven policy proof

Fixtures contain expected verdicts and failure reasons. `self-test` runs them without mutating canonical registry/output files. Required fixture families are enumerated in the spec and tasks.

### 7. CI integration

Extend the existing workflow instead of adding multiple workflows. Add provenance validation/generation checks while retaining Rust, SpecGrain, Diffcipline, and existing negative controls. Run core provenance validation on all three OSes if the implementation remains portable; keep adversarial fixture aggregation on Ubuntu where sufficient.

Workflow remains `contents: read` and actions remain pinned.

## Implementation sequence

### Phase A — policy/schema

1. reverify canonical base and Spec001 closure;
2. define policy schema and license dispositions;
3. define empty adoption registry schema;
4. define safe path/revision/digest validation contracts.

### Phase B — validator/generator

1. implement deterministic JSON loading and validation;
2. implement exact identity/license/adoption-mode checks;
3. implement local SHA-256/path verification;
4. implement Cargo lock closure;
5. implement notices and Himsat SBOM rendering;
6. implement generated-file drift check.

### Phase C — fixtures

Add positive and negative fixtures for allowed/manual/denied/unknown licenses, immutable revision, required paths, independent model/asset license, path traversal, digest mismatch, dependency closure, and output drift.

### Phase D — CI and proof

1. extend expected Diffcipline scope without weakening manifest policy;
2. run provenance validation/self-test/generation check in CI;
3. preserve existing Rust/SpecGrain/Diffcipline proof;
4. inspect exact-head results and failures;
5. repair forward only;
6. merge with expected-head protection;
7. verify exact canonical merge before closeout.

## Verification baseline

Expected implementation commands should include equivalents of:

```text
python tools/provenance.py validate
python tools/provenance.py check-generated
python tools/provenance.py self-test
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
```

The implementation PR must record actual commands/output rather than treating these examples as executed evidence.

## Failure cases

- malformed JSON/schema version;
- duplicate entry ID;
- unknown license;
- manual/denied license proposed for adoption;
- restricted source represented as COPY/DEPEND/VENDOR;
- symbolic or malformed Git revision;
- missing source path;
- unsafe path traversal;
- missing/invalid/mismatched SHA-256;
- model/data/asset missing independent terms;
- unregistered Cargo dependency;
- dependency identity/checksum mismatch where observable;
- notice/SBOM regeneration drift.

## Residual risks

- machine license classification is project policy, not legal advice;
- path-level license interpretation may require human review before creating a registry entry;
- Git/Cargo metadata formats can evolve, so parsers should reject unsupported state rather than guess;
- custom `himsat.sbom/v1` is not an industry-standard SBOM format;
- source digest verification cannot prove facts about remote bytes that were never materialized; future adoption PRs must provide the evidence object that the registry claims.

## Closeout rule

Specification 002 closes only after the machinery itself is merged, exact-head and post-merge CI pass, negative fixtures prove fail-closed behavior, generated outputs are reconciled, and no donor adoption has been smuggled into the unit.
